# 05 - Graphics composition

Scope: how a 64-bit server process paints the world into the frame of the original 32-bit
`CivilizationV_DX11.exe` (the "shell"). Covers the Gate 3 prototype of 2026-11-09 (x64 `shell_server.exe`, x86
`shell_composite.dll`, x86 `test_host.exe` stand-in), its measurements on the stand-in and inside the live game,
the structure of the game's D3D11 frame and where the server's image has to go into it, and the hazards found on
the way (Steam overlay recursion, CEG, a Lua-channel deadlock). Everything here is copied or synthesised from
`research/sources/`; nothing was re-measured. Where sources disagree, the files say so.

The idea in one paragraph (after REVIEW.md section 1 and GATES.md): the EXE keeps its window, swap chain, 2D UI
(Lua VM + Controls), audio, save/load and asset loading, with its world-rendering systems switched off through
`[DisableSystems]` in `config.ini`. A separate 64-bit process renders the world into a D3D11 texture created with
an NT handle and a keyed mutex. A small DLL loaded into the game opens that texture by name inside the game's own
D3D11 device and draws it as one fullscreen triangle at a point in the game's frame that lies after the scene clear
and before the units, flags, banners and HUD. The game then presents as usual, so the UI is exactly the original.

Verdict of Gate 3 (GATES.md, 2026-11-09 22:30): **GO WITH CONDITIONS** - the texture composites under the units
and UI in the live game at no measurable frame cost (+0.004 ms at ~280 fps), 2.5 ms latency, and survives minimise,
server restarts, AI turns, a 15.5-minute soak and (after a fix) the game's own resolution change. Conditions: a
real insertion point (deferred-context tagging), coexistence with other injectors, the 2 s retarget gap, and a list
of untested cases.
