## How the x86 behaviour was established

The closed libraries are repository files of the DLL fork (not game binaries): `FirePlace/lib/FireWorksWin32.obj` (an
archive of 33 non-LTCG members; `FireWorksWin32.lib` is LTCG IL and does not disassemble), `FirePlace/lib/FLuaWin32.lib`,
`CvGameCoreDLLUtil/lib/CvGameCoreDLLUtilWin32.lib`, `CvWorldBuilderMap/lib/CvWorldBuilderMapWin32.obj` (again the
non-LTCG twin). Disassembled with `llvm-objdump -d -r -C` 19.1.7; functions grouped by normalised instruction shape
(`evidence/2026-11-10-1006/splitdis.py`); string literals behind `$SG` relocations resolved per archive member
(`coffstr.py`, needed because every member reuses the same `$SG` names). Shape listings:
`dllutil-enum-serializer-shapes.txt`, `fdatastream-scalar-shapes.txt`.

## Byte format facts (for the save audit, issue 1004)

All [C] from the x86 disassembly; widths are the same on x64 because every type below is fixed-width on both.

| Item | Bytes on the stream |
|---|---|
| Enum serializers (`CvGameCoreDLLUtil`), every enum except GameTypes | copied to `int`, `FDataStream::Write(const int&)`: 4 bytes LE. Reader: `Read(int&)`, stored as the enum. 80 writers and 80 readers share one instruction shape each (162 serializers in the library, 121 used). |
| **GameTypes** | **1 byte**: copied to `char`, `Write(const char&)`; reader `Read(char&)` + `movsbl` (sign-extend), so `GAME_TYPE_NONE` (-1) round-trips. The only 1-byte enum serializer. |
| bool, char, unsigned char | 1 byte raw (`WriteIt(1, p)`) |
| short, unsigned short | 2 bytes |
| int, unsigned int, **unsigned long**, float | 4 bytes. `unsigned long` is its own overload and stays 4 bytes on x64 (LLP64) |
| __int64 | 8 bytes, swapped on endianness mismatch through `FEndian::SwapEndian<__int64>` |
| unsigned __int64 | 8 bytes, **never swapped** (x86 falls into FEndian's generic template, which only asserts) |
| GUID | 16 bytes raw |
| Endianness | every FDataStream is constructed `ENDIAN_LITTLE` (`m_eEndianness = 1`); `FEndian::GetEndianness()` returns 1; no swap ever happens in practice |
| `FDataStream::Write(const std::string&)` | 4-byte **signed** length (`Write(int)`), then the bytes, no terminator; nothing for an empty string beyond the length |
| `operator<<(FDataStream&, const std::string&)` | 4-byte **unsigned** length (`Write(unsigned int)`), then one 1-byte `Write(char)` per character: the same bytes |
| `FDataStream::Read(std::string&)` | via `ReadString`: 4-byte length; if `0 < len <= GetSizeLeft()` reads `len` bytes; if `len < 0` or `len > GetSizeLeft()` calls `RaiseException(runtime_error("FDataStream ReadString error"))` |
| `operator>>(FDataStream&, std::string&)` | 4-byte unsigned count, then `count` single-byte reads (no size check) |
| std::wstring | not implemented here: no wstring stream member is referenced by the DLL (issue 1004 records the x86 format: 4-byte count, 2 bytes per character) |
| FDataStream layout | x86: vptr, `bool m_bEnableCB` (+4), `m_eEndianness` (+8), `m_uiBytesRead` (+0xC), `m_uiPosition` (+0x10). Vtable order = header order; the DLL calls `ReadIt` (+4), `WriteIt` (+8), `GetSizeLeft` (+0x34), `RaiseException` (+0x3C). Both sides compile from the same header on x64. |
| FAutoArchive::saveDelta (OOS sync, not save data) | 4-byte count of changed variables; per variable, in `std::set<FAutoVariableBase*>` order (**by pointer value**, so allocation-dependent), its 4-byte index in `m_contents` (skipped if absent), then the variable's own `saveDelta` |

**FCRC (feeds info-type hashes and the save header's game-data hash):** reflected table, polynomial `0xEDB88320`,
table entry i = 8 shift/xor steps of i; `Calc(p, n, crc)` runs `crc = (crc >> 8) ^ table[(crc ^ *p++) & 0xFF]` while
`n != 0` and returns `crc` **with no final XOR** [C: the x86 `FCRC::Calc` ends with `retl $0xc` straight after the
loop]. Default initial value `CRC_INIT = ~0`. So `g_CRC32.Calc(s, n)` = standard CRC-32 of s, bitwise inverted
(check: `Calc("123456789", 9) ^ 0xFFFFFFFF == 0xCBF43926` [L]). `m_magic` = Calc of four zero bytes from ~0.

## FireWorks members that call into the host executable

On x86 each resolves `GetProcAddress(GetModuleHandleA(NULL), "<name>")` once, caches it in a static and jumps to it
(`FireWorksWin32.obj`, relocation strings) [C]. The x64 replacements use the same names, so the server must export
them (x64 C names, no decoration). A missing export makes x86 jump to address 0; x64 logs a FATAL stub line, flushes
the stub log and aborts.

| DLL symbol | EXE export(s) | Behaviour |
|---|---|---|
| `FIFileSystem::GetInstance()` | `GetFileSystemMgr` | returns the export's `FIFileSystem&` |
| `FILogFileMgr::GetInstance()` | `GetLogFileMgr` | returns the export's `FILogFileMgr&` |
| `FStringA_GetStringInitData()` | `FStringA_GetStringInitData` | shared empty-string header (12 zero bytes + NUL) |
| `FStringW_GetStringInitData()` | `FStringW_GetStringInitData` | same, wide |
| `FireMallocAlignedNoTracking(size, align, file, line)` | `FSBABind`: `GetSmallObjectAllocator`, `FSBAAllocate`, `FSBADeallocate`, `FSBADisable`, `FSBAIsDisabled`, `FSBAIsSmallBlock`, `FSBAHasAllocatorForSize`, `FSBAGetMaxAllocatorSize`, `FSBAPreventCreation` | all nine must resolve, else CRT only for good; then `GetSmallObjectAllocator(false)` must be non-NULL (retried per call until it is); then `FSBAAllocate((size + align - 1) & ~(align - 1))`, falling back to `_aligned_malloc(size, align)`; non-power-of-two or zero alignment goes straight to `_aligned_malloc` |
| `FireFreeAlignedNoTracking(p)` | same binding | `FSBADeallocate(p)` if bound; `_aligned_free(p)` when it returns false |
| `FireMallocNoTracking` / `FireFreeNoTracking` (not census symbols) | same binding | as above with `malloc`/`free`; needed because `FAutoVariableBase`'s VPDEBUG-only `FCallStack` member (FSTLBlockAllocator) is now constructed and destroyed in this library |

`FDebugHelper::GetInstance` is not a trampoline: x86 `LoadLibraryA("kernel32.dll")` + `RtlCaptureStackBackTrace`,
then `SymInitialize`. Not reproduced (stub).

## Quirks kept for x86 parity

- `FStringW::ExtractFileTitle` returns the file name **with** its extension: x86 calls `szDest.Mid(szDest, 0, iDot)`
  and `Mid` returns without doing anything when source and destination share a buffer [C]. The DLL stores the result
  as the world builder map name (`CvWorldBuilderMapLoader.cpp:1325`).
- `FSerialization::toString(unsigned int)` uses `"%ud"` (number then `d`), `toString(unsigned char)` `"%uhh"` (number
  then `hh`), `toString(char)` `"%hh"` (unterminated conversion; empty under VC9 [I]). OOS debug text only; built
  without sprintf because the UCRT treats those formats as invalid parameters.
- `toString(DirectionTypes)` maps -1..6 by the x86 jump table (the original Firaxis enum); Vox Populi moved
  `NO_DIRECTION` to 7, which x86 already prints as `INVALID ENUM VALUE` [C].
- `FMemoryStream::CopyToMem` copies from the current position, not the start; `Init(size, data, true)` with a
  non-NULL `data` keeps the caller's buffer and later frees it with `delete []` [C].
- Exceptions: x86 throws a sliced `stdext::exception` copy whose `what()` is `"unknown"`; x64 throws a sliced
  `std::exception` whose `what()` keeps the message. Same type of catch site behaviour for `catch (std::exception&)`
  and `catch (...)`; different text.

## Notes for the build and the other workers

- **VPDEBUG mismatch:** `build_stubs.py --config debug` does not define `VPDEBUG`; `build.py --config debug` does.
  `FAutoVariableBase` has three extra members under `VPDEBUG` (`FAutoVariableBase.h:104-109`). The x86 lib was built
  without them, so on x86 the DLL's derived classes carry members the lib constructor never initialises. On x64 the
  replacement constructs them when built with `VPDEBUG`; built without (today's build_stubs.py debug) it behaves like
  x86. Recommend build_stubs.py use the DLL's predefs per config.
- **FLua split with 1005** (decided by the coordinator): 1006 defines `Value()`, `~Value()`, `Value::Unref`,
  `Value::Push`, `Table::Push`, `Details::Error` and `ErrorHandler::operator()`; 1005 defines `Value(lua_State*, int)`,
  `Value::Set` and `Details::CCallWithErrorHandling`. The x86 disassembly of those three (FLuaWin32.lib) for 1005's
  [I] notes: `Value(L, idx)` sets `{L, LUA_NOREF}`, `lua_checkstack(L, 1)`, `lua_pushvalue(L, idx)`,
  `m_iRef = luaL_ref(L, LUA_REGISTRYINDEX)`: nil is stored (luaL_ref gives `LUA_REFNIL`, and `Valid()` is then
  true). `Set` unrefs the old value first, then does the same. `CCallWithErrorHandling` holds
  `FLua::ms_CriticalSection` around `lua_cpcall`; on failure calls `Details::HandleCPCallError(L, rc)` then
  `lua_settop(L, -2)` [C].
- `luaL_unref` is used only by FLua, so it is not among the 336 census symbols; 1005's real Lua provides it.
- `CvWorldBuilderMap` objects are statics of `CvWorldBuilderMapLoader.cpp`, constructed during DLL static
  initialisation: their constructors here do not call `STUB_CALL`.
- The census grouping is by name pattern. Real homes differ for `FSerialization::toString(ActivityTypes/DirectionTypes)`
  (CvGameCoreDLLUtil, listed under FireWorks) and `FStringW::CopyToUTF8` (FireWorks, listed under CvGameCoreDLLUtil);
  the files follow the real library.
